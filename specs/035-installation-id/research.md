# Research: Installation ID

**Feature**: 035-installation-id
**Date**: 2026-03-13

## R1: Installation Model Design

**Decision**: The `Installation` model will be a simple SQLModel table, NOT inheriting from `BaseResource` or any of the standard base classes.

**Rationale**: The standard base classes (`BaseResource`, `NamedResource`, `Resource`) provide features designed for user-facing API resources: `labels`, `created_by`, `updated_by`, `deleted_at`, soft-delete support, and filterable/sortable ClassVars. The Installation entity is an internal system singleton — it has no user owner, no name, no labels, no soft-delete lifecycle. Inheriting from `BaseResource` would add 6+ unused columns and inappropriate behaviors.

**Alternatives considered**:
- Inherit from `BaseResource`: Rejected — adds `labels`, `created_at`, `updated_at` columns that are unnecessary for a singleton record. The `created_at`/`updated_at` columns use `server_default=text("now()")` which is appropriate, but the rest is overhead.
- Use raw SQLAlchemy table: Rejected — the project constitution mandates SQLModel for all data models.

## R2: UUID Generation in Migration

**Decision**: Generate the UUID using PostgreSQL's `gen_random_uuid()` function within the Alembic migration's `INSERT` statement. This ensures the UUID is created atomically as part of the schema migration.

**Rationale**: The existing codebase uses `server_default=text("now()")` for timestamps, demonstrating the pattern of using PostgreSQL functions for default values. Using `gen_random_uuid()` follows the same pattern. The migration both creates the table and inserts the singleton row, ensuring the installation_id exists immediately after migration.

**Alternatives considered**:
- Generate UUID in Python (migration code): Rejected — the UUID should be generated by the database for consistency with the existing pattern of using server-side defaults. However, for the INSERT in the migration, we'll use `uuid.uuid4()` in the Python migration code since `gen_random_uuid()` requires the pgcrypto extension which may not be available. SQLAlchemy's `op.execute()` with a Python-generated UUID is simpler and more portable.
- Generate at application startup: Rejected — spec says "database initialization," and creating in migration ensures the ID exists before any application code runs.

**Revised Decision**: Generate UUID via Python's `uuid.uuid4()` in the Alembic migration's data migration step. The migration creates the table and inserts a single row with the generated UUID.

## R3: Telemetry Identifier Derivation

**Decision**: Use SHA-256 hash of `f"{installation_id}:{db_host}:{db_name}"` to derive the telemetry identifier. The output is a hex string.

**Rationale**: SHA-256 is a standard collision-resistant hash function available in Python's `hashlib` standard library. The colon separator prevents ambiguity between components (e.g., host "a:b" + name "c" vs host "a" + name "b:c" is not possible since colons are not valid in PostgreSQL hostnames or database names). The resulting hex string is 64 characters, suitable for use as a Segment `anonymousId`.

**Alternatives considered**:
- MD5: Rejected — not collision-resistant, though collisions are not a practical concern at this scale.
- HMAC with a secret key: Rejected — adds unnecessary complexity. The goal is uniqueness across environments, not cryptographic security.
- Raw concatenation without hashing: Rejected — would expose database connection details in telemetry events.

## R4: Reading Installation ID at Startup

**Decision**: Add a function `get_installation_id()` in the telemetry module that reads the installation ID from the database. Call it during `initialize_telemetry()` (which already runs at startup in both the API server and Temporal worker).

**Rationale**: The `initialize_telemetry()` function (in `src/nexus/telemetry/client.py`) is already the established initialization point, called in both `src/nexus/api/main.py:136` and `src/nexus/workflows/workflow_engine/services/temporal_worker.py:103`. It currently reads `entitlement_id` from settings. The change is to also read `installation_id` from the database and derive the telemetry identifier.

**Alternatives considered**:
- Read in settings (config layer): Rejected — settings are loaded from environment variables, not from the database.
- Create a separate initialization function: Rejected — would require changes to all startup entry points. Using the existing `initialize_telemetry()` is simpler.

## R5: TelemetryClientRegistry Changes

**Decision**: Modify `TelemetryClientRegistry.initialize()` to accept an `anonymous_id` parameter (the derived telemetry identifier). Use `anonymous_id` as the Segment `anonymousId` (via the `client.track()` call). Always include `entitlement_id` as a property in the event properties (empty string when not configured) — it is NOT used as the Segment `userId`.

**Rationale**: The `entitlement_id` is supplementary metadata for Red Hat to correlate telemetry with subscriptions. It belongs in the event properties alongside other telemetry data, not as the Segment `userId` which has identity-resolution semantics. Always including it (even when empty) ensures a consistent event schema and simplifies downstream analytics queries.

**Alternatives considered**:
- Use `entitlement_id` as Segment `userId`: Rejected — `userId` triggers Segment identity resolution and merging. The `entitlement_id` is optional supplementary context, not a primary identity.
- Drop `entitlement_id` from Segment calls entirely: Rejected — spec FR-006 requires it to be included when configured.

## R6: Entitlement ID Configuration

**Decision**: Keep `NEXUS_ENTITLEMENT_ID` environment variable as the configuration mechanism for the optional `entitlement_id`. No changes to the configuration system needed.

**Rationale**: The existing `TelemetrySettings.entitlement_id` field (in `src/nexus/core/config/base.py:937-940`) already reads from `NEXUS_ENTITLEMENT_ID` with a default of empty string. The spec says to make it optional — it already is. The only change is in how it's used: it becomes `userId` in Segment instead of being the sole identifier.

**Alternatives considered**:
- Store `entitlement_id` in the database: Rejected — this is a configuration value that comes from external systems (AAP). Environment variables or runtime settings are the appropriate storage.
- Remove the env var: Rejected — existing deployments rely on it.

## R7: Singleton Enforcement

**Decision**: Use a database CHECK constraint or single-row enforcement pattern. The simplest approach: use a table with a single column `id` (UUID, primary key) and no auto-incrementing or additional columns that would allow multiple rows. The migration inserts exactly one row. Application code only reads, never inserts.

**Rationale**: Since the row is created by the migration, application code never needs to insert. The table structure itself (primary key on UUID) prevents duplicate UUIDs, and the migration logic only inserts if the table is empty. This is sufficient for FR-003.

**Alternatives considered**:
- Add a CHECK constraint `id = 1` on an integer column: Rejected — over-engineering for a migration-created singleton.
- Use a key-value settings table: Rejected — the Installation entity is semantically distinct from application settings.

## R8: Database Connection Coordinates

**Decision**: Use the `db_host` and `db_name` values from `DatabaseSettings` (the configured connection string values, not resolved DNS). These are read via `get_settings().db_host` and `get_settings().db_name`.

**Rationale**: The configured values are stable across container restarts (same connection string). DNS-resolved addresses can change with infrastructure but the configured service name (e.g., `postgres.default.svc.cluster.local`) remains constant. This addresses the edge case in spec line 80 — the telemetry identifier only changes if the operator explicitly changes the database connection configuration, not due to infrastructure-level DNS changes.

**Alternatives considered**:
- Query `SELECT inet_server_addr()` from PostgreSQL: Rejected — returns the server's IP which changes with infrastructure.
- Use the full `database_url`: Rejected — contains credentials that should not be hashed into telemetry identifiers.
