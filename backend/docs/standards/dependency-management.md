# Dependency Management Standards

This document defines dependency management standards for the Nexus Python monorepo.

## Package Manager

Use `uv` exclusively for all dependency management operations. Do not use `pip`, `poetry`, or other package managers.

## File Roles

### pyproject.toml

Source of intent for dependency constraints. Declares version ranges using semantic versioning patterns.

- Defines production dependencies in `[project.dependencies]`
- Defines development dependencies in `[project.optional-dependencies.dev]`
- Specifies Python version requirement: `requires-python = ">=3.12,<3.14"`

### uv.lock

Source of truth for reproducibility. Contains exact pinned versions with cryptographic hashes.

- Autogenerated by `uv sync`
- Never edit manually
- Commit with every pyproject.toml change

### requirements.txt

Production dependencies exported from uv.lock for hermetic builds (Konflux).

- Autogenerated by `uv export`
- Includes exact versions and cryptographic hashes
- Excludes dev dependencies, editable installs, and workspace references
- Generation command: `uv export --frozen --python=3.12 --no-dev --no-editable --no-emit-workspace --output-file requirements.txt`

### requirements-build.txt

Build-time dependencies for hermetic/offline container builds.

- Manually curated
- Includes `uv` and `hatchling` with cryptographic hashes

## Version Pinning Strategy

Choose the appropriate constraint pattern based on the library's maturity and stability:

### Stable, Mature Libraries (minimum version only)

For libraries with strong semver guarantees and stable APIs:

```
"asyncpg>=0.30.0"
"redis>=7.1.0"
"pydantic>=2.0.0"
"alembic>=1.12.0"
```

**When to use**: well-established libraries (1.0+) with a track record of semver compliance.

### Libraries with Known Breaking Changes (upper bound)

For libraries that have a history of breaking changes in minor versions:

```
"fastapi>=0.104.0,<0.122"
"sqlalchemy[asyncio]>=2.0.0,<2.0.45"
"ruff>=0.1.0,<0.14.4"
"mypy>=1.6.0,<1.19"
```

**When to use**: libraries that introduce API changes or deprecations frequently.

### Pre-1.0 Libraries (strict minor version control)

For libraries under active development without semver guarantees:

```
"sqlmodel>=0.0.14,<0.0.28"
"langchain-mcp-adapters>=0.1.0,<0.2.0"
"pymupdf>=1.26.6,<1.27.0"
```

**When to use**: all libraries with major version 0.x, where minor version bumps may break compatibility.

### Development Dependencies

Apply the same patterns to dependencies in `[project.optional-dependencies.dev]`. Treat linters, type checkers, and test frameworks with the same care as production dependencies.

## Adding a New Dependency

1. Add the dependency to `pyproject.toml` with appropriate version constraint:
   ```toml
   [project.dependencies]
   "new-library>=1.2.0,<2.0.0"
   ```

2. Update uv.lock:
   ```bash
   uv sync --extra dev
   ```

3. Update requirements.txt:
   ```bash
   make sync-requirements
   ```

4. Commit all three files together:
   - pyproject.toml
   - uv.lock
   - requirements.txt

Never commit only pyproject.toml or only uv.lock. All three files must be synchronized.

## Removing a Dependency

1. Remove the dependency from `pyproject.toml`

2. Update uv.lock:
   ```bash
   uv sync --extra dev
   ```

3. Update requirements.txt:
   ```bash
   make sync-requirements
   ```

4. Commit all three files together

5. Search for imports and references:
   ```bash
   grep -r "import removed_library" src/ tests/
   ```

## Updating Dependencies

### Automated Updates (Renovate)

Renovate bot automatically creates PRs for dependency updates:

- Schedule: before 6am Monday
- Strategy: `in-range-only` (only updates within declared version ranges)
- Grouping: all Python dependencies grouped into a single PR
- Auto-merge: **disabled** - all PRs require manual review and approval

Review Renovate PRs for:
- Breaking changes in release notes
- Test failures in CI
- Performance regressions
- **Snyk SCA vulnerability findings** (see Vulnerability Scanning below)

### Manual Updates

To update a specific dependency:

1. Modify the version constraint in pyproject.toml (if needed)

2. Run:
   ```bash
   uv sync --extra dev --upgrade-package <package-name>
   make sync-requirements
   ```

3. Commit pyproject.toml, uv.lock, and requirements.txt together

To update all dependencies within constraints:

```bash
uv sync --extra dev --upgrade
make sync-requirements
```

## Python Version Policy

Supported Python versions: `>=3.12,<3.14`

CI matrix tests on:
- Python 3.12
- Python 3.13

When adding a new Python version:
1. Update `requires-python` in pyproject.toml
2. Add version to CI matrix in `.github/workflows/ci.yml`
3. Add classifier to `[project.classifiers]`

## Vulnerability Scanning

### Snyk SCA (Software Composition Analysis)

All dependency updates are automatically scanned for known vulnerabilities using Snyk SCA:

**When it runs:**
- On every pull request (Python and npm dependencies)
- Scheduled daily at 2:23 PM UTC
- On pushes to `devel` branch
- On-demand via workflow_dispatch

**What it checks:**
- Python dependencies (via `requirements.txt`)
- npm dependencies (via `package.json` in `frontend/`)

**Severity thresholds:**
- **HIGH/CRITICAL**: Blocks PR merge (CI fails)
- **MEDIUM/LOW**: Reported but does not block merge

**Workflow files:**
- `.github/workflows/sast-snyk-backend.yml` - Backend SAST & SCA
- `.github/workflows/sast-snyk-frontend.yml` - Frontend SAST & SCA

### Manual Review Policy

All dependency update PRs require manual review and approval before merge:

**Review checklist:**
- Verify no HIGH or CRITICAL vulnerabilities detected by Snyk SCA
- Review breaking changes in release notes
- Confirm all CI checks pass
- Assess security advisory details if vulnerabilities are present

**Security-first approach:**
Auto-merge is disabled to ensure human review of all dependency changes and prevent potential malware/attack risks.

### Responding to Vulnerability Alerts

When Snyk SCA detects a HIGH/CRITICAL vulnerability:

1. **Review the security advisory**: understand the impact and affected versions
2. **Check for available fix**: determine if a patched version exists
3. **Assess applicability**: confirm if the vulnerability affects your usage
4. **Remediation options:**
   - Update to a patched version (preferred)
   - Apply a workaround if no patch is available
   - Accept the risk if impact is negligible (requires security review)
5. **Document decision**: add comment to PR explaining the chosen approach

For MEDIUM/LOW severity findings:
- Review during normal PR review process
- Plan remediation during next dependency update cycle

## Enforcement

### Pre-commit Hook

The `sync-requirements` pre-commit hook automatically runs when `uv.lock` or `pyproject.toml` changes:

```yaml
- id: sync-requirements
  name: sync requirements.txt with uv.lock
  entry: make
  args: [sync-requirements]
  language: system
  pass_filenames: false
  files: ^(uv\.lock|pyproject\.toml|requirements\.txt)$
```

### CI Checks

The Konflux requirements sync workflow fails if requirements.txt is out of sync:

```yaml
- name: Check requirements.txt sync
  run: make sync-requirements
```

If CI fails on requirements sync:
1. Run `make sync-requirements` locally
2. Commit the updated requirements.txt
3. Push the commit

## Common Pitfalls

### Forgetting to Sync requirements.txt

**Wrong**:
```bash
uv sync --extra dev
git add pyproject.toml uv.lock
git commit -m "Add new dependency"
```

**Correct**:
```bash
uv sync --extra dev
make sync-requirements
git add pyproject.toml uv.lock requirements.txt
git commit -m "Add new dependency"
```

The pre-commit hook will catch this, but it's better to sync proactively.

### Using Overly Broad Constraints

**Wrong**:
```toml
"pydantic>=2.0.0"  # for a pre-1.0 library
```

**Correct**:
```toml
"sqlmodel>=0.0.14,<0.0.28"  # strict minor control for 0.x
```

### Manually Editing uv.lock or requirements.txt

Never edit these files manually. Always regenerate them:

- uv.lock: `uv sync --extra dev`
- requirements.txt: `make sync-requirements`

## Tooling vs Convention

**Enforced by tooling:**

- `sync-requirements` pre-commit hook (catches out-of-sync requirements.txt)
- CI requirements sync check (fails build if requirements.txt diverges)
- `uv sync` validates dependency resolution (catches conflicts)
- `uv.lock` integrity (cryptographic hashes prevent tampering)

**Convention only:**

- Version constraint strategy (minimum-only vs upper-bounded vs strict minor)
- Committing all three files together (pyproject.toml, uv.lock, requirements.txt)
- Dependency review for Renovate PRs
- Python version policy updates
